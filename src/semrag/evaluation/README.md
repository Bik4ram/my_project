# `src/semrag/evaluation` — Evaluation harness

The query-time evaluation subsystem. Owns the machinery that
turns a list of curated `GoldenQuery` items into per-query
metrics, an aggregate report, and (optionally) an LLM-judge
self-evaluation pass over the final answers. Eval is a
**query-time consumer** — it does not write to the index, it
only reads from retrieval and reasoning and reports on the
quality of what came back.

Two distinct evaluators exist today:

- **`EvaluationHarness`** (`harness.py`) — retrieval-quality
  metrics: precision/recall at k, MRR, NDCG, hit rate,
  average rank, and primary/secondary file recall. Runs the
  retriever and the prompt builder; does not call the LLM.
- **`EndToEndEvaluator`** (`evaluator.py`) — full-pipeline
  evaluation: drives `QueryService.ask()` for every golden
  query, runs the citation validator on the answer, and
  (optionally) calls the LLM a second time as a self-eval
  judge scoring correctness, groundedness, completeness,
  hallucination risk, and citation quality 1-10.

Plus three supporting modules:

- **`metrics.py`** — the eight retrieval-metric primitives
  (precision, recall, MRR, NDCG, hit rate, average rank,
  file recall). Pure functions; no I/O.
- **`models.py`** — the Pydantic models that describe
  golden queries, per-query results, the coverage report,
  and the aggregate report.
- **`benchmarks.py`** — a curated list of `GoldenQuery`
  items, with `expected_intent` and `repo_area` enums for
  slicing. The canned benchmark set for the SemRAG
  repository itself (project `semrag`), used for
  regression tracking.
- **`benchmarks_rtl_uvm.py`** — the RB-04 benchmark set:
  50 curated `GoldenQuery` items for the `rtl_uvm`
  project (a SystemVerilog/UVM testbench corpus). Ground
  truth is repository-grounded — every `relevant_chunk_ids`
  entry was validated against the authoritative 467-chunk
  corpus, never generated by the retriever. Separate from
  the `semrag` set in `benchmarks.py`; both are exposed via
  `get_rtl_uvm_benchmarks()` and the analogous
  `get_benchmarks()` accessor. See §1.1.
- **`citation_validator.py`** — a real, deterministic
  check that every `[Source: …]` reference in an LLM
  response corresponds to a path that was in the
  retrieved context. The groundedness check that does
  not require a second LLM.

This is **not** a benchmarking dashboard, **not** an
LLM-judge prompt catalog, and **not** a guide to
*creating* golden queries. For those, see
[`docs/developer_guide.md`](../../../docs/developer_guide.md)
and the existing benchmark file.

---

## 1. Purpose of the package

The evaluation package exists to answer two questions:

> 1. **Is the retrieval pipeline returning the right
>    chunks?** (precision, recall, MRR, NDCG, file
>    recall — measured against a curated ground truth)
> 2. **Are the LLM's answers grounded in the retrieved
>    context?** (citation validity, fabrication rate,
>    optional LLM-judge self-eval)

Three things make that harder than "compare a list to
a list":

1. **Two ways to measure relevance.** The `GoldenQuery`
   carries both `relevant_chunk_ids` (chunk-level
   relevance — the strict view) and `primary_files` /
   `secondary_files` (path-level relevance — the
   "did the retriever surface the right file at all"
   view). Both are valid; the harness reports both.
2. **Citation validity is real, but it's not
   faithfulness.** A response can cite a real path
   and still hallucinate the prose around the
   citation. The citation validator catches the
   unambiguous case (path was never in context) and
   leaves the harder case to the LLM judge.
3. **The LLM judge is best-effort.** The same model
   that produced the answer is asked to score it.
   The harness reports the judge scores with
   `llm_scores.valid` to flag parse failures, and
   `mean_*` aggregates only over the `valid` ones.

Everything else in the package — the per-stage
metric breakdown, the coverage report sliced by
area/intent, the latency p50/p95 — exists to make
the first three points land well in practice.

## 2. Package structure

```
evaluation/
├── __init__.py               (empty)
├── models.py                 Pydantic models: RepoArea, ExpectedIntent,
│                             GoldenQuery, RetrievalMetrics, EvalQueryResult,
│                             CoverageReport, AggregateReport
├── metrics.py                precision_at_k, recall_at_k, reciprocal_rank,
│                             ndcg_at_k, hit_rate, average_rank, file_recall
│                             (pure functions, no I/O)
├── citation_validator.py     CitationValidationResult + validate_citations
│                             (regex-based, no LLM)
├── harness.py                EvaluationHarness (retrieval + prompt builder,
│                             no LLM; produces AggregateReport)
├── evaluator.py              EndToEndEvaluator (full pipeline + citation
│                             validator + LLM judge; produces
│                             EvalAnswerReport)
└── benchmarks.py             BENCHMARKS list + get_benchmarks() +
                              get_benchmarks_by_area() +
                              get_benchmarks_by_intent()
```

`__init__.py` is empty. Callers always import from the
submodule path
(`semrag.evaluation.harness.EvaluationHarness`,
`semrag.evaluation.evaluator.EndToEndEvaluator`). Same
convention used by every other package.

## 3. Module responsibilities

### `models.py`

The Pydantic data model. Two enums and five BaseModel
classes.

**Enums:**

- `RepoArea` — coarse package-level area the question
  targets (`CORE`, `INGESTION`, `STORAGE`, `RETRIEVAL`,
  `REASONING`, `API`, `EVALUATION`, `CONFIG`, `GENERAL`).
  Used for the coverage report's `by_area` slice.
- `ExpectedIntent` — coarse intent class the question
  is *expected* to elicit (`ARCHITECTURE`,
  `VERIFICATION`, `RTL`, `DEBUG`, `CONFIG`, `API`,
  `GENERAL`). Note this is **not** the same vocabulary
  as the retrieval layer's `QueryIntent` enum
  (`semrag.retrieval.intent.QueryIntent`); the eval
  side uses a finer-grained enum (includes `RTL`,
  `API`, `CONFIG`) because the benchmark
  questions target specific subsystem areas. Used
  for the coverage report's `by_intent` slice.

**Models:**

- `GoldenQuery` — one benchmark question. Carries
  `query_id`, `project_id`, `query_text`,
  `relevant_chunk_ids` (chunk-level ground truth),
  `primary_files` / `secondary_files` (path-level
  ground truth; primary = must appear, secondary =
  should appear), `expected_intent`,
  `repo_area`, and a free-form `description`.
- `RetrievalMetrics` — per-query retrieval metrics
  produced by the harness: precision/recall at k,
  MRR, NDCG, primary/secondary file recall, hit
  rate, average rank, plus the found/missed file
  lists.
- `EvalQueryResult` — per-query result the harness
  produces: `query_id`, `query_text`, `metrics`,
  `latency_ms`, `retrieved_paths`,
  `estimated_total_tokens`, `excluded_chunk_count`.
- `CoverageReport` — the per-benchmark-run coverage
  summary: total/primary/secondary counts and
  ratios, plus `by_area` and `by_intent` slices.
- `AggregateReport` — top-level harness result:
  `query_count`, the eight `mean_*` aggregates,
  `coverage`, `latency_p50_ms`, `latency_p95_ms`,
  and the full `per_query_results` list.

### `metrics.py`

Eight pure functions, no I/O, no state:

- **`precision_at_k(retrieved, relevant, k)`** — hits
  in top-k divided by k.
- **`recall_at_k(retrieved, relevant, k)`** — hits in
  top-k divided by total relevant. Returns 0.0 when
  relevant is empty.
- **`reciprocal_rank(retrieved, relevant)`** — 1/rank
  of the first relevant hit; 0.0 if no relevant hit.
- **`ndcg_at_k(retrieved, relevant, k)`** — Discounted
  Cumulative Gain normalized by ideal DCG. Returns
  0.0 when relevant is empty or k ≤ 0.
- **`hit_rate(retrieved, relevant)`** — 1.0 if any
  relevant hit; 0.0 otherwise. Returns 0.0 when
  relevant is empty.
- **`average_rank(retrieved, relevant)`** — mean rank
  of all relevant hits. Returns `float("inf")` when
  no relevant hit; the harness filters `inf` out
  before averaging so the aggregate is finite.
- **`file_recall(retrieved_files, expected_files)`** —
  |expected ∩ retrieved| / |expected|. Returns 1.0
  when expected is empty (a "no expectation, no
  failure" convention).

All eight take simple Python collections (`list[str]`,
`set[str]`) and return `float`. They are pure, easy to
unit-test in isolation, and shared between the harness
and the end-to-end evaluator.

### `citation_validator.py`

`validate_citations(response_text, included_chunks)
-> CitationValidationResult`. The single check that
does not need an LLM.

- The response is scanned with a regex
  (`_CITATION_PATTERN = re.compile(r"\[Source:\s*([^,\]]+?)(?:,\s*lines\s+(\d+)-(\d+))?\]")`)
  for every `[Source: <path>]` or `[Source: <path>,
  lines X-Y]` reference.
- `included_chunks` is the list of `RetrievalResult`
  the LLM was actually given (the citation
  validator does not invent this list; the caller
  reconstructs it from the prompt).
- A citation is `valid` if its path appears in
  `included_chunks.relative_path`; otherwise it is
  `fabricated`.

Returns `CitationValidationResult` with
`cited_paths`, `valid_citations`,
`fabricated_citations`, plus
`has_fabricated_citations` and `fabrication_rate`
properties.

The module docstring is explicit: this is a
**necessary-but-not-sufficient groundedness check**,
not a full faithfulness evaluator. A response can
cite a real path and still hallucinate the prose
around the citation; that case is left to the LLM
judge. What this catches is the unambiguous case
(a path that was never in context) and is presented
as exactly that.

### `harness.py`

`EvaluationHarness(retriever, embed_query_fn, k=10,
use_prompt_builder=True)`. The retrieval-quality
evaluator. Two methods:

- **`evaluate_query(golden_query) -> EvalQueryResult`** —
  embed the query, run `HybridRetriever.retrieve` for
  one `GoldenQuery`, time the call, compute all eight
  metrics, optionally build the prompt to report
  `estimated_total_tokens` and `excluded_chunk_count`,
  return the per-query result.

- **`evaluate_all(golden_queries) -> AggregateReport`** —
  iterate `evaluate_query` over the list, compute
  eight `mean_*` aggregates, p50/p95 latency, and
  the coverage report sliced by area and intent.

The harness does not call the LLM. The retrieved
paths and the prompt's token estimate are recorded
for the operator's inspection; the LLM's answer is
not part of the harness's contract — that's
`EndToEndEvaluator`.

Default `k=10` matches the retrieval layer's
`DEFAULT_FINAL_TOP_K`. The `use_prompt_builder` flag
exists so a benchmark can be run in
"retrieval-only" mode (skip the prompt builder
entirely) when the prompt-budget signal is not
relevant.

### `evaluator.py`

`EndToEndEvaluator(query_service)`. The full-pipeline
evaluator. One method:

- **`evaluate_all(golden_queries, run_llm_judge=True)
  -> EvalAnswerReport`** — drive
  `QueryService.ask()` for every `GoldenQuery`,
  extract citation data from the response, optionally
  call the LLM a second time to score the response.

For each query:

1. `query_service.ask(project_id, query_text)` returns
   a `QueryAnswer` with `final_answer`,
   `iterations_used`, `hit_iteration_limit`, `messages`,
   and `debug` (if available).
2. The answer's citations are extracted and validated
   against the chunks the LLM was given (reconstructed
   from the user message's `[Source: …]` headers by
   `_extract_chunks_from_messages`).
3. If `run_llm_judge=True` and the LLM is reachable,
   the LLM is called a second time with `_JUDGE_PROMPT`
   (a fixed prompt asking for 1-10 scores on five
   dimensions) and the JSON response is parsed via
   `_parse_judge_scores`.
4. Per-query results are aggregated into
   `EvalAnswerReport`.

`EvalAnswerResult` carries:

- The final answer text.
- `citation_recall`, `citation_precision`,
  `hallucination_rate` (all derived from
  `valid_count` / `fabricated_count` / `total_cited`).
- `cited_paths`, `fabricated_paths`,
  `valid_citations_count`,
  `fabricated_citations_count`.
- `llm_scores` (an `LLMJudgeScores` dataclass with
  `correctness`, `groundedness`, `completeness`,
  `hallucination_risk`, `citation_quality`,
  each 1-10) — may be `None` if the judge was
  skipped or the LLM's response didn't parse.
- `latency_ms`, `iterations_used`,
  `hit_iteration_limit`, `error` (any exception
  from `query_service.ask` is captured and recorded
  on the result; the loop continues).

`EvalAnswerReport` carries the eight
`mean_*` aggregates (four ground-truth + five
LLM-judge), `latency_p50_ms`, `latency_p95_ms`,
and the full `per_query_results` list.

### `benchmarks.py`

A curated list of `GoldenQuery` items, plus three
helpers:

- `BENCHMARKS: list[GoldenQuery]` — the canned
  benchmark set the team uses for regression
  tracking. 18 queries spanning the SemRAG
  codebase itself. `repo_area` breakdown:
  RETRIEVAL (7), CORE (2), INGESTION (2),
  STORAGE (2), REASONING (2), CONFIG (1),
  API (1), EVALUATION (1). `expected_intent`
  breakdown: ARCHITECTURE (12), CONFIG (3),
  VERIFICATION (2), API (1).
- `get_benchmarks() -> list[GoldenQuery]` — returns
  a copy of `BENCHMARKS`.
- `get_benchmarks_by_area(area: RepoArea) -> list[GoldenQuery]`.
- `get_benchmarks_by_intent(intent: ExpectedIntent) -> list[GoldenQuery]`.

The benchmark questions target the SemRAG
codebase itself — they ask about retrieval,
ingestion, the agent loop, observability, and the
evaluation framework, with `primary_files` /
`secondary_files` pointing at the actual source
files. This makes the benchmark a regression
suite for "does SemRAG answer questions about
SemRAG correctly," which is a real and useful
shape — but the framework is generic; new
benchmark sets (per project) are added by
constructing more `GoldenQuery` lists.

### `benchmarks_rtl_uvm.py`

The RB-04 benchmark set, built to give the
retrieval-quality freeze a second, independent
ground truth on a foreign corpus (the `rtl_uvm`
SystemVerilog/UVM testbench project):

- `PROJECT_ID = "rtl_uvm"` — every `GoldenQuery`
  in this module targets project `rtl_uvm`.
- `BENCHMARKS_RTL_UVM: list[GoldenQuery]` — 50
  curated queries. Category mix: navigation 8,
  design 8, debug 8, assertions/SVA 5, bus 6,
  UVM 6, log 4, terminology 5.
- `get_rtl_uvm_benchmarks() -> list[GoldenQuery]` —
  returns a copy of `BENCHMARKS_RTL_UVM`.
- `_gq(...)` — a local helper that builds a
  `GoldenQuery` with `repo_area=GENERAL`
  (`repo_area` describes SemRAG's own modules, so
  every foreign-project query is GENERAL) and the
  `expected_intent` label carried on the query.

Ground truth is **repository-grounded, never
generated by the retriever**: every
`relevant_chunk_ids` entry was validated against
the authoritative 467-chunk corpus for `rtl_uvm`
(94 relevant chunk IDs across 47 unique chunks),
and the content spot-checks were reviewed by hand
during RB-04. The set is intentionally separate
from `benchmarks.py` so the two projects never
share relevance judgments. The validation tests
live in
`tests/unit/evaluation/test_benchmarks_rtl_uvm.py`.

## 4. Evaluation pipeline

The two evaluators are independent and can be
run separately. The end-to-end evaluator
internally runs the retrieval-quality path (via
`QueryService.ask`), but does not share state
with the harness.

```text
  golden_queries: list[GoldenQuery]
       │
       ├────── EvaluationHarness.evaluate_all ────────────────────┐
       │                                                            │
       │   for each golden_query:                                   │
       │     1. embed(query_text)                                    │
       │     2. HybridRetriever.retrieve(...)                        │
       │     3. compute metrics.py primitives                        │
       │     4. (optional) PromptBuilder.build(...)                  │
       │   aggregate mean_*, latency p50/p95, coverage              │
       │       by area / by intent                                    │
       │                                                            ▼
       │                                                  AggregateReport
       │
       └────── EndToEndEvaluator.evaluate_all ──────────────────────┐
                                                                    │
            for each golden_query:                                  │
              1. QueryService.ask(project_id, query_text)           │
                 → final_answer, iterations_used,                   │
                   hit_iteration_limit, messages, debug             │
              2. citation_validator.validate_citations(             │
                   final_answer, included_chunks                    │
                 )                                                  │
                 → cited_paths, valid_count,                        │
                   fabricated_count                                  │
              3. (optional) LLM judge via _JUDGE_PROMPT             │
                 → LLMJudgeScores (correctness,                     │
                   groundedness, completeness,                      │
                   hallucination_risk, citation_quality)            │
              4. capture latency, error (if any)                    │
            aggregate mean_*, latency p50/p95                        │
                                                                    ▼
                                                        EvalAnswerReport
```

### 4.1 Why two evaluators

The harness is **retrieval-quality only** — it does
not call the LLM, does not run `QueryService`, and
produces deterministic numbers in seconds. This is
the right tool for "did the retriever regress?"

The end-to-end evaluator is the **full pipeline**
— it drives `QueryService.ask`, gets the LLM's
answer, and reports on citation validity and (via
the LLM judge) answer quality. This is the right
tool for "did the user-visible answer regress?"

Both exist because they answer different
questions on different cadences. The harness
runs on every PR (CI); the end-to-end evaluator
runs nightly or on-demand (slower, costs LLM
inference, dependent on the model).

### 4.2 What the harness produces

For every `GoldenQuery`:

- `precision_at_k`, `recall_at_k`,
  `reciprocal_rank`, `ndcg_at_k`,
  `primary_file_recall`, `secondary_file_recall`,
  `hit_rate`, `average_rank`.
- The found/missed file lists
  (`primary_files_found`,
  `primary_files_missed`, etc.).
- `latency_ms` (the wall-clock time of
  `HybridRetriever.retrieve`).
- `estimated_total_tokens` and
  `excluded_chunk_count` (only if
  `use_prompt_builder=True`).

For the aggregate:

- The eight `mean_*` aggregates
  (`mean_average_rank` is computed over
  finite ranks only; `float("inf")` is filtered
  out).
- `latency_p50_ms`, `latency_p95_ms`.
- `coverage` — a `CoverageReport` with
  totals, ratios, and `by_area` /
  `by_intent` slices.

### 4.3 What the end-to-end evaluator produces

For every `GoldenQuery`:

- `final_answer` (the LLM's response).
- `citation_recall`, `citation_precision`,
  `hallucination_rate` (from the citation
  validator; the three are all
  `valid_count / total_cited` /
  `fabricated_count / total_cited`).
- `cited_paths`, `fabricated_paths`,
  `valid_citations_count`,
  `fabricated_citations_count`.
- `llm_scores` (the LLM judge's 1-10 scores
  on five dimensions; may be `None` if the
  judge was skipped or the response didn't
  parse).
- `latency_ms` (from
  `QueryAnswer.debug.llm_latency_ms` if
  available).
- `iterations_used`,
  `hit_iteration_limit`.
- `error` (any exception from
  `query_service.ask` is captured and
  recorded; the loop continues to the next
  query).

For the aggregate:

- The four `mean_*` ground-truth aggregates
  (citation recall, precision, hallucination
  rate, context utilization).
- The five `mean_*` LLM-judge aggregates
  (correctness, groundedness, completeness,
  hallucination risk, citation quality),
  computed over the queries whose
  `llm_scores.valid` is `True`.
- `latency_p50_ms`, `latency_p95_ms` (only
  over queries with `latency_ms > 0`).

## 5. Dataset handling

The dataset is a `list[GoldenQuery]`. There's no
dataset loader, no JSONL reader, no factory — the
benchmark set is a Python literal in
`benchmarks.py`, and new benchmark sets are
constructed as new `GoldenQuery` lists.

### 5.1 `GoldenQuery` shape

```python
GoldenQuery(
    query_id: str,
    project_id: str,
    query_text: str,
    relevant_chunk_ids: set[str] = set(),
    primary_files: set[str] = set(),
    secondary_files: set[str] = set(),
    expected_intent: ExpectedIntent = GENERAL,
    repo_area: RepoArea = GENERAL,
    description: str = "",
)
```

Three relevance signals, all optional but at
least one should be set:

- **`relevant_chunk_ids`** — chunk-level ground
  truth. The strict view. Use this when a
  human has marked specific chunk IDs as
  relevant (typically by inspecting the index
  and noting which chunks would answer the
  question). Drives `precision_at_k`,
  `recall_at_k`, `reciprocal_rank`,
  `ndcg_at_k`, `hit_rate`, `average_rank`.
- **`primary_files`** — path-level ground
  truth, must-appear. The retriever is
  expected to surface at least one chunk
  from each of these files in the top-k.
  Drives `primary_file_recall` and the
  `primary_files_found` / `primary_files_missed`
  lists. The coverage report aggregates
  these.
- **`secondary_files`** — path-level ground
  truth, should-appear. Supporting context.
  Drives `secondary_file_recall` and the
  matching found/missed lists. Lower stakes
  than `primary_files`; a missed secondary
  file does not count as a hard failure.

### 5.2 Why both chunk-level and path-level

`relevant_chunk_ids` is what a careful human
curator would write. But the chunk IDs are
internal identifiers — a deterministic string
`"<project_id>::<relative_path>::<chunk_kind>::<disambiguator>"`
(see `semrag.ingestion.chunking.id_scheme.chunk_id`).
If the chunker changes for a file (different
`chunk_kind`, different disambiguator — e.g.
the chunker is updated, or a file is re-scanned
with a new parser result), chunk IDs shift and
the curated set becomes stale. `primary_files`
and `secondary_files` are robust to chunk-ID
shifts because the path is what the engineer
actually cares about.

The harness reports both. A high
`primary_file_recall` with a low
`recall_at_k` is a signal: the retriever is
finding the right files but the right chunks
within those files aren't ranked high enough.
A high `recall_at_k` with a low
`primary_file_recall` is the opposite.

### 5.3 Slicing

`get_benchmarks_by_area(area)` and
`get_benchmarks_by_intent(intent)` return
filtered lists. The coverage report
additionally groups by area and intent in
the aggregate — `by_area` and `by_intent`
in the `CoverageReport`. This is what makes
"did retrieval regress on the *config*
subsystem?" answerable.

## 6. Query execution

Both evaluators call into the same retriever
and the same prompt builder. The harness
calls them directly; the end-to-end evaluator
goes through `QueryService.ask`.

### 6.1 The harness path

```python
query_embedding = embed_query_fn(golden_query.query_text)
results = retriever.retrieve(
    golden_query.query_text,
    query_embedding,
    project_id=golden_query.project_id,
    top_k=self._k,
    filters=VectorSearchFilter(project_id=golden_query.project_id),
)
```

The `embed_query_fn` is a constructor argument
to the harness (not the LLM provider, not the
embedding provider — a callable that takes a
string and returns a `list[float]`). The
harness does not know which embedding provider
is in use; the caller wires it. This is the
same pattern used by
`SearchCodebaseTool` in
`semrag.reasoning.agents.tools`.

`filters=VectorSearchFilter(project_id=...)`
matches what every other call site does —
retrieval is project-scoped.

`latency_ms` is the wall-clock time of
`retriever.retrieve`, measured with
`time.perf_counter()` and reported on the
`EvalQueryResult`. The aggregate computes p50
and p95 from the per-query latencies.

### 6.2 The end-to-end path

```python
answer: QueryAnswer = query_service.ask(
    golden_query.project_id,
    golden_query.query_text,
)
```

`QueryService.ask` runs the full pipeline:
retrieval → prompt builder → agent loop → final
answer. The end-to-end evaluator does not
intervene; it consumes the `QueryAnswer`.

If `ask` raises, the exception is captured
on the `EvalAnswerResult` (via
`f"{type(exc).__name__}: {exc}"`), the loop
continues to the next query, and the report
records the partial run. A failed query
contributes nothing to the aggregates.

### 6.3 What query execution does **not** do

- **Cache results across runs.** Both evaluators
  are re-runnable; nothing is memoized. A
  repeated run will hit the index and the LLM
  every time.
- **Throttle LLM calls.** The LLM judge fires
  one extra `complete` per query when
  enabled. A benchmark with 100 queries = 100
  LLM-judge calls. Throttle upstream in
  `Settings.llm_*` if needed.
- **Parallelize queries.** Both evaluators
  iterate sequentially. Parallel evaluation
  is a future change; today the bottleneck
  is the LLM, not the evaluator.

## 7. LLM judge

The end-to-end evaluator's optional second-pass
LLM call. The model that produced the answer is
asked to score it.

### 7.1 The judge prompt

`_JUDGE_PROMPT` is a fixed string constant. It
asks for 1-10 scores on five dimensions:

- `correctness` — factually correct based on
  the context?
- `groundedness` — claims supported by the
  citations?
- `completeness` — fully addresses the
  question?
- `hallucination_risk` — 1=very safe,
  10=very risky.
- `citation_quality` — valid, specific,
  well-used?

The model is instructed to respond with valid
JSON only, no other text:

```json
{"correctness": <int>, "groundedness": <int>,
 "completeness": <int>, "hallucination_risk":
 <int>, "citation_quality": <int>}
```

### 7.2 Score parsing

`_parse_judge_scores(raw)` does the minimum to
turn the LLM's response into an
`LLMJudgeScores` dataclass:

- Empty / `None` content → returns `None`.
- JSON parse error → returns `None`.
- Non-integer values → returns `None`.
- Score outside 1-10 → `LLMJudgeScores.valid`
  is `False` (the dataclass is constructed
  with the values, but the aggregate skips
  invalid scores via the `valid` property).

The aggregate computes `mean_*` over the
queries with `llm_scores.valid == True` only.
Invalid scores are silently excluded from the
mean; they appear on the per-query result
for inspection but do not pollute the
aggregate.

### 7.3 What the LLM judge does **not** do

- **Validate the judge is calibrated.** A 1-10
  scale is whatever the model says it is. The
  judge is best-effort; the harness reports
  what the model returned.
- **Use a different model than the answer.**
  Same model, same prompt template, same
  context. A second model (e.g. a dedicated
  judge) is a future change.
- **Score the retrieval in isolation.** That's
  the harness's job. The judge scores the
  *answer*, not the chunks.
- **Generate explanations.** The judge
  returns JSON scores, not free text. Add
  free-text when an eval needs
  per-failure-dimension rationale.

### 7.4 Honesty about the judge

The module docstring says it: "All metrics are
best-effort — no guarantee the LLM faithfully
self-evaluates." The LLM judge is a useful
*signal*, not a ground truth. The harness
reports it; operators should treat it as one
input among several, not as a verdict.

## 8. Metrics collection

`metrics.py` is the heart of the
retrieval-quality evaluation: eight pure
functions, all stateless, all O(n) or O(n log n)
in the length of the retrieved list.

### 8.1 The eight primitives

| Function                            | Returns                         | Edge cases                            |
| ----------------------------------- | ------------------------------- | ------------------------------------- |
| `precision_at_k(r, rel, k)`         | hits_in_top_k / k               | k ≤ 0 → 0.0; top_k empty → 0.0        |
| `recall_at_k(r, rel, k)`            | hits_in_top_k / |relevant|      | relevant empty → 0.0                  |
| `reciprocal_rank(r, rel)`           | 1/rank_of_first_hit             | no hit → 0.0                          |
| `ndcg_at_k(r, rel, k)`              | DCG / IDCG                      | relevant empty or k ≤ 0 → 0.0         |
| `hit_rate(r, rel)`                  | 1.0 if any hit, else 0.0        | relevant empty → 0.0                  |
| `average_rank(r, rel)`              | mean rank of relevant hits      | no hit → `float("inf")`               |
| `file_recall(r_files, e_files)`     | |e ∩ r| / |e|                  | e empty → 1.0 (vacuous)                |
| `validate_citations(text, chunks)`  | `CitationValidationResult`      | empty response → empty result         |

`average_rank`'s `float("inf")` is the
convention the harness filters out before
aggregating. Any other convention (e.g. `None`,
`-1`) would require a sentinel check at every
metric call site; `inf` propagates through
arithmetic cleanly because the harness
explicitly skips it.

`file_recall`'s vacuous-truth case (empty
expected set) returns 1.0 because "the
retriever found everything we asked for, given
that we asked for nothing" is true, and an
expected-empty question shouldn't penalize the
retriever.

### 8.2 Aggregation

`EvaluationHarness.evaluate_all` does the
aggregations:

- `mean_*` for the eight metrics. For
  `mean_average_rank`, only finite ranks
  contribute.
- `latency_p50_ms` = sorted
  `latencies[len(latencies) // 2]`.
- `latency_p95_ms` =
  `latencies[min(int(len(latencies) * 0.95),
  len(latencies) - 1)]`.
- `coverage` — a `CoverageReport` with totals,
  primary/secondary ratios, and
  `by_area` / `by_intent` slices.

`EndToEndEvaluator._aggregate` does the same
for the answer-level metrics, skipping queries
with parse-failed or skipped LLM judge.

### 8.3 What metrics collection does **not** do

- **Compute confidence intervals.** The
  aggregates are point estimates over the
  benchmark. A bootstrap CI is a future
  addition.
- **Normalize across benchmarks.** The
  `mean_*` is over the queries in this run.
  Comparing two runs is the caller's
  responsibility.
- **Detect regression automatically.** The
  harness reports; a downstream CI gate
  decides whether the change is acceptable.

## 9. Reporting

The two evaluators each produce a single
top-level report object. There's no
HTML/PDF/JSONL emitter; the report is a
Pydantic model the caller serializes
however it wants.

### 9.1 `AggregateReport` (the harness)

```python
AggregateReport(
    query_count: int,
    mean_precision_at_k: float,
    mean_recall_at_k: float,
    mean_mrr: float,
    mean_ndcg_at_k: float,
    mean_hit_rate: float,
    mean_average_rank: float,
    mean_primary_recall: float,
    mean_secondary_recall: float,
    coverage: CoverageReport,
    latency_p50_ms: float,
    latency_p95_ms: float,
    per_query_results: list[EvalQueryResult],
)
```

The `coverage` field is itself a
`CoverageReport`:

```python
CoverageReport(
    total_queries: int,
    total_primary: int,
    total_secondary: int,
    primary_found: int,
    secondary_found: int,
    primary_recall: float,
    secondary_recall: float,
    by_area: dict[str, dict[str, float]],
    by_intent: dict[str, dict[str, float]],
)
```

Each `by_area` / `by_intent` slice carries the
per-bucket primary/secondary totals, found
counts, and recall ratios.

### 9.2 `EvalAnswerReport` (the end-to-end evaluator)

```python
EvalAnswerReport(
    query_count: int,
    mean_citation_recall: float,
    mean_citation_precision: float,
    mean_hallucination_rate: float,
    mean_context_utilization: float,
    mean_correctness: float,
    mean_groundedness: float,
    mean_completeness: float,
    mean_hallucination_risk: float,
    mean_citation_quality: float,
    latency_p50_ms: float,
    latency_p95_ms: float,
    per_query_results: list[EvalAnswerResult],
)
```

Each `EvalAnswerResult` carries the full per-query
detail (final answer, citation analysis, LLM
judge scores, latency, iterations, error).

### 9.3 Serialization

Both reports are Pydantic `BaseModel`
subclasses. `report.model_dump()` produces
a JSON-ready dict. A CLI that wants JSON
output should `json.dumps(report.model_dump())`
— the harness does not ship a CLI today; the
operator constructs one from the report.

### 9.4 What reporting does **not** do

- **Render a dashboard.** The reports are
  data; visualization is downstream.
- **Compare against a baseline.** A regression
  detector is a future change. Today the
  operator compares two `model_dump()` outputs.
- **Emit to a metrics backend.** The harness
  is not a Prometheus exporter. Aggregate
  numbers can be piped into a custom sink
  by the caller; the harness itself does not
  register a metric.

## 10. Extension points

| Need                                          | Touch                                  | What to add                                   |
| --------------------------------------------- | -------------------------------------- | --------------------------------------------- |
| New retrieval metric                          | `metrics.py`                           | Pure function; add to `RetrievalMetrics` model and `EvaluationHarness.evaluate_query` |
| New coverage slice                            | `models.py` (`CoverageReport`) + `harness.py` (`_build_coverage_report`) | New `by_<dimension>` field on `CoverageReport`; populate in `_build_coverage_report` |
| New benchmark question                        | `benchmarks.py`                        | New `GoldenQuery` literal in `BENCHMARKS`     |
| New benchmark set per project                 | New module next to `benchmarks.py`     | A `BENCHMARKS_<name>: list[GoldenQuery]` constant; export a `get_<name>_benchmarks()` helper |
| New LLM judge dimension                       | `evaluator.py` (`_JUDGE_PROMPT`, `LLMJudgeScores`) | New field on the dataclass; new line in the prompt; new `mean_*` field on `EvalAnswerReport`; new line in `_aggregate` |
| New retrieval evaluator                      | New module next to `evaluator.py`      | A class taking whatever it needs; produces a `*Report` model; not coupled to the existing evaluators |
| New citation check                            | `citation_validator.py`                | New function; returns a new result type; harness / evaluator calls it alongside `validate_citations` |
| New query-level error capture                 | `evaluator.py` (`_evaluate_single`)    | Capture the new exception; add a field to `EvalAnswerResult` |
| New aggregate (e.g. bootstrap CI)            | `harness.py` (`evaluate_all`)          | New field on `AggregateReport`; new aggregation in the function |

Two extension points are deliberately **not**
available:

- **Loading benchmark questions from a file.**
  The benchmark is a Python literal today;
  loading from JSONL is a future change.
  Keeping it a Python literal means the
  benchmark can be statically inspected and
  curated as code.
- **Replacing `MockLLM` for the judge.** The
  judge always uses the configured LLM. A
  dedicated judge model is a future change.

## 11. Common debugging paths

| Symptom                                                | Look first                                                                                  |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| `mean_average_rank` is `inf`                            | At least one query had no relevant hit. Filter finite ranks before averaging — the harness does this; a custom consumer of `RetrievalMetrics` may not |
| `mean_citation_precision` is 0.0                       | Every answer had a fabricated citation; check the prompt's `[Source: …]` format and the citation validator regex |
| `LLMJudgeScores.valid` is `False`                      | The LLM's response wasn't parseable as the expected JSON; check the prompt and the LLM's output verbosity |
| `EvalAnswerResult.error` is set                        | `QueryService.ask` raised; check the error type and message — `LLMProviderError`, `ValueError`, etc. |
| `latency_p95_ms` is 0                                  | No queries with `latency_ms > 0`; the harness doesn't time queries where the retriever raises, the evaluator doesn't time queries where `QueryAnswer.debug` is `None` |
| `mean_*` aggregates look wrong                         | Empty benchmark set → all `mean_*` are 0.0 (not NaN); the harness returns an empty `AggregateReport` rather than raising |
| `primary_file_recall` is 0 but `recall_at_k` is high   | The retriever is finding relevant chunks but not the primary *files*; usually means the path-level ground truth is wrong, or the chunker split the primary file across many chunks |
| `citation_recall` and `citation_precision` are equal   | They're computed the same way (`valid_count / total_cited`); a real divergence would require the validator to know which citations are *necessary* (it doesn't today) |
| `EndToEndEvaluator` crashes on import                  | `QueryService` is not constructed; the evaluator takes the service in the constructor, never imports it directly. Build the service first |
| `CitationValidationResult.cited_paths` is empty       | The LLM didn't emit any `[Source: …]` references; the validator can't flag what wasn't claimed. This is itself a finding — the prompt asks for inline citations |
| `by_area` slice is empty for an area                   | No queries in this benchmark target that area; add `GoldenQuery` items with that `repo_area` |
| `by_intent` slice shows `unknown`                     | A `GoldenQuery` has no `expected_intent` set; the default is `GENERAL`, but the `unknown` label comes from a different code path — check the `expected_intent` field on every `GoldenQuery` |
| New metric doesn't appear in `AggregateReport`         | The field is added to `RetrievalMetrics` but the aggregate doesn't read it; check `evaluate_all` after editing the model |

## 12. Common mistakes

1. **Confusing the two `QueryIntent` enums.** The
   retrieval layer's `QueryIntent` (`ARCHITECTURE`,
   `VERIFICATION`, `DEBUG`, `GENERAL`) is not
   the same as the eval layer's `ExpectedIntent`
   (`ARCHITECTURE`, `VERIFICATION`, `RTL`,
   `DEBUG`, `CONFIG`, `API`, `GENERAL`). The
   eval enum is finer-grained because the
   benchmark questions target specific subsystem
   areas. A `GoldenQuery.expected_intent` of
   `RTL` has no `QueryIntent` counterpart.
2. **Setting `primary_files` to a directory
   rather than a file path.** The harness
   matches on `relative_path` exactly. A
   directory prefix in `primary_files` will
   never match a chunk's `relative_path`.
3. **Setting `relevant_chunk_ids` without
   inspecting the index.** The chunk IDs are
   deterministic strings of the form
   `"<project_id>::<relative_path>::<chunk_kind>::<disambiguator>"`
   (`semrag.ingestion.chunking.id_scheme.chunk_id`);
   they are not the `query_id` or the file path.
   Curate chunk IDs by running a query and
   noting which `chunk_id` values surface in the
   `EvalQueryResult.retrieved_paths` /
   debug-artifacts `chunks/chunk_metadata.json`.
4. **Treating the LLM judge as ground truth.**
   The judge is best-effort. Use it as one
   signal among several; never make a
   pass/fail decision on judge scores alone.
5. **Running the end-to-end evaluator
   without an LLM reachable.** The
   `QueryService.ask` call requires an LLM.
   Use `MockLLM` for offline tests, but
   don't expect the judge to fire — `MockLLM`
   returns scripted responses that won't
   parse as the judge's JSON.
6. **Comparing two `AggregateReport`s
   without aligning the benchmark set.**
   A change in the benchmark questions
   invalidates the comparison. The benchmark
   set is a versioned artifact; changes go
   through review.
7. **Treating `latency_p95_ms` as a
   service-level indicator.** The
   evaluator's p95 is over the *benchmark
   queries*, not production traffic. It's
   useful for "did the retriever slow down?"
   not for SLO measurement. The latter is
   the perf suite's job.
8. **Forgetting that `EvalAnswerResult.error`
   means the query didn't contribute to
   aggregates.** A query that crashed during
   `ask` is recorded but excluded from the
   `mean_*` calculations. A benchmark with
   20% errors will look better than it is.
9. **Adding a new benchmark question without
   `description`.** The `description` is
   what makes the benchmark reviewable. A
   `GoldenQuery` with no description is
   effectively undocumented.
10. **Mutating `BENCHMARKS` in place.**
    The helpers return *copies* of the list
    (`return list(BENCHMARKS)`), so
    appending to a helper's return value
    doesn't pollute the global. But
    in-place mutation of `BENCHMARKS`
    itself would persist across the
    process.
11. **Trusting `mean_context_utilization`**
    The harness sets it to 0.0 (no
    implementation populates it). Don't
    read it as a measured signal; it's a
    placeholder for a future metric.
12. **Catching `LLMProviderError` in
    `_llm_judge` and re-raising.** The
    judge returns `None` on any
    exception; the aggregate skips
    queries without a judge. Catching
    and re-raising would break the
    `evaluate_all` flow and produce a
    partial report.

## 13. Architectural boundaries

What the evaluation package **does not** do:

- **Write to the index.** Eval is a
  query-time consumer. The benchmark
  questions, the metrics, the reports —
  all read-only.
- **Define the LLM provider.** `QueryService`
  does. The end-to-end evaluator takes a
  `QueryService` and uses its
  `_llm` for the judge; the evaluator
  does not build its own LLM.
- **Define the embedding provider.** The
  harness takes an `embed_query_fn`
  callable. The caller wires the real
  provider.
- **Render a dashboard.** The reports
  are Pydantic models; visualization
  is downstream.
- **Run as part of every PR.** The
  harness is fast enough for CI; the
  end-to-end evaluator is not (it makes
  LLM calls). CI runs the harness; the
  end-to-end evaluator runs on a
  schedule.
- **Compute faithfulness.** The
  citation validator catches the
  unambiguous case (path was never
  in context). The LLM judge scores
  five dimensions best-effort. Full
  faithfulness measurement requires
  a human or a second model with
  ground truth — neither is in this
  package.
- **Compare against a baseline.** The
  reports are point estimates; the
  operator compares two outputs.
- **Migrate the schema.** The eval
  queries the index but doesn't
  write to it; schema changes are
  Alembic's.

What it **does** own:

- The eight retrieval-metric
  primitives (`metrics.py`).
- The `GoldenQuery`, `RetrievalMetrics`,
  `EvalQueryResult`, `CoverageReport`,
  `AggregateReport` data models
  (`models.py`).
- The citation validator and the
  `CitationValidationResult` model
  (`citation_validator.py`).
- The `EvaluationHarness` and its
  per-query / aggregate computation
  (`harness.py`).
- The `EndToEndEvaluator`, the
  `EvalAnswerResult` /
  `EvalAnswerReport` data classes,
  the `_JUDGE_PROMPT`, and the
  score-parsing helper
  (`evaluator.py`).
- The `BENCHMARKS` list and the
  `get_benchmarks` / `get_benchmarks_by_area` /
  `get_benchmarks_by_intent` helpers
  (`benchmarks.py`).
- The per-query latency timing
  (the harness times
  `HybridRetriever.retrieve`; the
  evaluator reads
  `QueryAnswer.debug.llm_latency_ms`).

## Skipped (and why)

- **JSONL benchmark loading.** The benchmark
  set is a Python literal in
  `benchmarks.py`; loading from JSONL would
  be a future change. Keeping it a Python
  literal means the benchmark can be
  statically inspected and curated as code.
- **Faithfulness measurement.** Requires a
  human or a second model with ground
  truth; the citation validator catches
  the unambiguous case (path was never in
  context), the LLM judge scores five
  dimensions best-effort. Neither is a
  full faithfulness evaluator.
- **Confidence intervals on aggregates.**
  The `mean_*` are point estimates. A
  bootstrap CI is a future change.
- **A dedicated judge model.** The judge
  uses the same LLM as the answer. A
  separate judge model (e.g. a larger
  model) is a future change.
- **Per-failure-dimension rationale from
  the judge.** The judge returns JSON
  scores, not free text. Add free-text
  when an eval needs per-failure
  rationale.
- **Regression detection.** The reports
  are point estimates; the operator
  compares two outputs. An automated
  baseline tracker is a future change.
- **A CLI for the evaluators.** The
  harness and evaluator are Python
  classes; serialization is the
  caller's job. A `python -m` CLI is a
  future change.
- **Parallel query evaluation.** Both
  evaluators iterate sequentially.
  Parallel evaluation is a future change
  (today the bottleneck is the LLM, not
  the evaluator).
- **A `mean_context_utilization` metric.**
  The harness records
  `EvalQueryResult.estimated_total_tokens`
  and `excluded_chunk_count` but does
  not derive a `context_utilization`
  ratio. The aggregate's
  `mean_context_utilization` is 0.0
  (no implementation populates it).
  Add when the metric is defined.
- **Citation *recall* in the strict
  sense.** The harness computes
  `citation_recall = valid_count /
  total_cited` — that's citation
  *precision* (of the citations
  emitted, what fraction is valid).
  True citation recall (of the
  citations that *should* be emitted,
  what fraction is) requires a
  ground-truth citation set, which the
  benchmark does not carry.
- **Per-iteration LLM-call metrics.**
  The end-to-end evaluator records
  `iterations_used` and
  `hit_iteration_limit` per query but
  does not aggregate them. Add a
  `mean_iterations_used` and an
  `iteration_limit_hit_rate` to the
  report when the agent loop is the
  regression target.
- **A real-benchmark integration test
  for the harness against the live
  `HybridRetriever`.** The
  `tests/unit/evaluation/` tests
  exercise the harness against a
  fixture; a real-benchmark test is
  `tests/unit/evaluation/test_harness_integration.py`
  (already exists). Future changes
  to the benchmark set should
  update that test's expected
  numbers, not add a new one.
